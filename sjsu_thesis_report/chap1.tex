\chapter{Introduction}

Machine learning has dramatically changed how computers are able to accomplish difficult tasks from identifying objects within images to driving cars autonomously. 
In supervised machine learning, a model is trained by comparing its results with an existing dataset which is the ground truth. 
In contrast to this type of learning, reinforcement learning (RL) is a method for learning based upon experience; i.e., RL agents learn through direct interaction with their environments using trial and error. 
Each time the agent interacts with its environment, the agent observes the current state of the environment, takes some action and then receives a reward signal to indicate how good or bad that action was. 
Through repeated interaction with the environment, the agent learns a policy - a mapping of states to actions - that will maximize the total rewards received at all times.

Training an RL agent involves two alternating phases. In the \emph{rollout phase}, the agent interacts with the environment using its current policy, collecting a batch of experiences consisting of observations, actions, and rewards. In the \emph{training phase}, the agent uses this collected experience to update its policy through gradient-based optimization. The agent's policy is represented by a neural network, and training adjusts the network's parameters to increase the probability of actions that led to higher rewards. This cycle of collecting experience and updating the policy repeats until the agent achieves satisfactory performance.

\section{Actor-Critic Methods}

In modern RL, we decompose the agent into two components: an actor and a critic. The actor is simply the policy network, which chooses the next action based upon its current knowledge of the environment. The critic is another independent network whose function is to estimate the total ``value'' associated with a particular state. That is, if the agent is in some state and follows its policy from that state forward, what would be the sum of rewards it receives? The critic estimates this quantity.

To train both the actor and the critic, we first calculate an ``advantage'' for every action taken by the agent by comparing what the agent actually got as a return versus what the critic estimated. A positive advantage means the action performed better than expected, while a negative advantage means it performed worse. The actor and critic networks are then updated so the probability of actions leading to positive advantage increases and vice-versa.

Proximal Policy Optimization (PPO), which was developed by Schulman et al.~\cite{ppo2017}, extends the general actor-critic framework through bounding how much the policy changes with respect to the amount of data used in an update; thus, potentially reducing the likelihood of large-scale destabilization in training. To improve sample efficiency, at the cost of increased computation per batch, PPO trains using batches that are reused over multiple training epochs. The reuse of batches, however, creates a communication problem among nodes in the distributed environment because each epoch in a PPO iteration involves exchanging gradients throughout the entire network split.

\section{Distributed Training}

Distributed training addresses the resource limitations of a single device by spreading computation across multiple machines. The simplest approach is \emph{centralized training}: an edge device such as a robot or sensor collects observations from the environment and sends them to a powerful cloud server, which runs the entire neural network and returns actions or updated model parameters. This works well when the model fits in the cloud server's memory and network bandwidth is sufficient for transmitting raw observations.

However, when a model is too large for a single device's memory, or when we want to keep parts of the computation close to the data source, we need a different strategy. \emph{Pipeline parallelism} partitions the neural network into sequential stages, with each stage running on a separate device. For example, a CNN feature extractor can run on one machine while the policy and value networks run on another. During the forward pass, the first machine processes raw observations into compact feature vectors and sends them to the second machine, which computes actions. During the backward pass for training, gradients flow in the reverse direction.

Pipeline parallelism introduces a communication challenge that centralized training does not face. In centralized training, the entire neural network resides on one machine, so all gradient computation and backpropagation happen locally in memory. The only network communication is the transfer of observations from the edge device to the cloud. In pipeline parallelism, the network split forces activations and gradients to be exchanged between machines for every minibatch during every training pass over the data. Since RL algorithms such as Proximal Policy Optimization (PPO)~\cite{ppo2017} reuse collected experience across multiple epochs for sample efficiency, this exchange is repeated many times per iteration, amplifying the communication overhead significantly.

\section{Communication Bottleneck}

Consider a concrete example. An RL agent learning from $96 \times 96$ RGB images with a batch of 4,096 steps per iteration and 10 update epochs of 32 minibatches each must exchange activations and gradients $10 \times 32 = 320$ times per iteration. Even after compressing observations through a CNN, the repeated gradient transmissions can exceed the total data volume of simply sending raw observations to a cloud server, as we quantify in Chapter~3. In bandwidth-constrained environments such as edge deployments or IoT networks, this communication overhead becomes the dominant bottleneck, slowing down training or making pipeline parallelism impractical altogether.

\section{Our Approach}

This project uses a technique called selective gradient transmission to alleviate the communication bottleneck. Instead of transmitting each minibatch’s full set of gradients from one machine to another after every minibatch, we have each machine store (accumulate) its gradients locally and then transmit only those gradients deemed most important based on their magnitude relative to some defined percentiles. If a gradient does not exceed its associated percentile it is stored in a ``local buffer'' and continues to be added to as it becomes large enough for transmission.

However, the use of buffers to store gradients can lead to the problem of stale gradients; since gradients that have been in storage for many iterations will likely represent old versions of the optimization space, by the time they are eventually sent they are unlikely to provide useful information about the current version of the optimization space. We propose using a decaying value (exponential decay) to penalize (discount) these older unsent gradients so that when gradients are eventually sent, the buffer contains a representation of the recent version(s) of the optimization space.

Our proposed solution was tested on the CarRacing-v3 environment, which involves learning how to control a car using $96 \times 96$ RGB images from the visual stream. We were able to reduce the network usage by 35\% while maintaining the baseline's quality with this approach.
