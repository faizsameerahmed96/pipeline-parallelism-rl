\chapter{Introduction}

Machine learning has dramatically changed how computers are able to accomplish difficult tasks from identifying objects within images to driving cars autonomously. 
In supervised machine learning, a model is trained by comparing its results with an existing dataset which is the ground truth. 
In contrast to this type of learning, reinforcement learning (RL) is a method for learning based upon experience; i.e., RL agents learn through direct interaction with their environments using trial and error. 
Each time the agent interacts with its environment, the agent observes the current state of the environment, takes some action and then receives a reward signal to indicate how good or bad that action was. 
Through repeated interaction with the environment, the agent learns a policy - a mapping of states to actions - that will maximize the total rewards received at all times.

In Deep Reinforcement Learning (DRL), the policy can be represented by a neural network. In on-policy DRL, the agent learns exclusively from experiences collected under its current policy. After each batch of experience is used to update the policy, it is discarded and new experience must be collected with the updated policy. This is in contrast to off-policy methods, which can reuse past experiences collected under older policies.

Training an on-policy DRL agent involves two alternating phases. In the \emph{rollout phase}, the agent interacts with the environment using its current policy, collecting a batch of experiences consisting of observations, actions, and rewards. In the \emph{training phase}, the agent uses this collected experience to update its policy through gradient-based optimization. The agent's policy is represented by a neural network, and training adjusts the network's parameters to increase the probability of actions that led to higher rewards. This cycle of collecting experience and updating the policy repeats until the agent achieves satisfactory performance.

\section{Actor-Critic Methods}

In modern RL, we decompose the agent into two components: an actor and a critic~\cite{konda1999}. The actor is simply the policy network, which chooses the next action based upon its current knowledge of the environment. The critic is another independent network whose function is to estimate the total ``value'' associated with a particular state. That is, if the agent is in some state and follows its policy from that state forward, what would be the sum of rewards it receives? The critic estimates this quantity.

To train both the actor and the critic, we first calculate an ``advantage'' for every action taken by the agent by comparing what the agent actually got as a return versus what the critic estimated. A positive advantage means the action performed better than expected, while a negative advantage means it performed worse. The actor and critic networks are then updated so the probability of actions leading to positive advantage increases and vice-versa.

Proximal Policy Optimization (PPO), which was developed by Schulman et al.~\cite{ppo2017}, extends the general actor-critic framework through bounding how much the policy changes with respect to the amount of data used in an update; thus, potentially reducing the likelihood of large-scale destabilization in training. To improve sample efficiency, at the cost of increased computation per batch, PPO trains using batches that are reused over multiple training epochs. The reuse of batches, however, creates a communication problem among nodes in the distributed environment because each epoch in a PPO iteration involves exchanging gradients throughout the entire network split.

\section{Distributed Training}

Deep Neural Networks are being used extensively in modern RL applications. These deep neural networks have large numbers of parameters, especially when the input dimensionality is high. As these networks grow in size and complexity, a significant amount of memory and computational resources required to perform the training process, which cannot fit on a single device. This is common in practical settings such as autonomous vehicles, where an on-board camera system may handle visual perception locally but must offload policy computation to a nearby edge server over a wireless link, or IoT sensor networks, where no single node has sufficient memory to host the full model and computation must be split across devices.

Distributed training addresses these resource limitations by spreading computation across multiple machines. The simplest approach is \emph{centralized training}: an edge device such as a robot or sensor collects observations from the environment and sends them to a powerful cloud server, which runs the entire neural network and returns actions or updated model parameters. This works well when the model fits in the cloud server's memory and network bandwidth is sufficient for transmitting raw observations.

However, when a model is too large for a single device's memory, or when we want to keep parts of the computation close to the data source, we need a different strategy. \emph{Pipeline parallelism} partitions the neural network into sequential stages, with each stage running on a separate device. For example, a CNN feature extractor can run on one machine while the policy and value networks run on another. During the forward pass, the first machine processes raw observations into compact feature vectors and sends them to the second machine, which computes actions. During the backward pass for training, gradients flow in the reverse direction.

Pipeline parallelism introduces a communication challenge that centralized training does not face. In centralized training, the entire neural network resides on one machine, so all gradient computation and backpropagation happen locally in memory. The only network communication is the transfer of observations from the edge device to the cloud. In pipeline parallelism, the network split forces activations and gradients to be exchanged between machines for every minibatch during every training pass over the data. Since RL algorithms such as Proximal Policy Optimization (PPO)~\cite{ppo2017} reuse collected experience across multiple epochs for sample efficiency, this exchange is repeated many times per iteration, amplifying the communication overhead significantly.

\section{Research Statement}

In pipeline-parallel RL training, a large amount of gradient data needs to be sent between devices during each training epoch and each mini-batch. This communication becomes a bottleneck, especially when devices are connected over bandwidth-constrained links.
This research addresses this bottleneck using selective gradient transmission. Instead of transmitting all gradients after every mini-batch, we allow gradients to accumulate locally and only transmit the most significant gradients as defined by a specified magnitude percentile threshold. All gradients with a magnitude less than the specified percentile are placed into a local buffer where they continue to accumulate until their magnitude surpasses the threshold.

One major issue with allowing gradients to accumulate prior to sending them is gradient staleness. By the time some gradients are actually sent, they can become stale. That is, the gradients accumulated earlier in the training process may represent the optimization space present at the beginning of training instead of the actual optimization space present when those gradients were sent. To help mitigate this issue, we add an exponential decay factor to discount older gradients which have yet to be sent. The result is that the buffer contains gradients representative of the recent optimization trends, rather than old signals.

We tested our method on the CarRacing-v3 domain. On this domain, we used a PPO agent to learn how to drive from $96 \times 96$ RGB images. We simulated pipeline parallelism between a CNN feature extractor and actor-critic network running in two separate Docker containers separated by a bridge network, and therefore constrained by a bandwidth-limited connection. With a 90th percentile threshold applied to the buffer with exponential decay, we were able to reduce cumulative data transfer by 35\%, and achieve equivalent or better policy performance than our uncompressed baseline.
